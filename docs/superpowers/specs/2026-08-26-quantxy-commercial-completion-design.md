# QuantXY 企业工作站商用全流程整改设计

**日期：** 2026-08-26  
**状态：** 单客户正式商业交付范围已锁定；实施、Staging 验证和 Internal/Customer Production 授权严格分离
**目标版本：** 所有纳入范围的模块全部达到商用验收门槛后一次性上线

## 1. 目标与已确认决策

本设计把 QuantXY 从“部分真实、部分演示、两套正式界面并存”的状态整改为单一、可审计、可测试、可恢复的企业工作站。

已确认的关键决策：

1. Next.js 是唯一正式商用界面。
2. 当前 fused HTML 仅作为迁移来源；功能迁完后下线，不长期维护双界面。
3. 当前交付对象是一家约 100 人企业；本期只运行一个正式租户，但核心表、RLS、Storage、缓存、向量索引、通知、定时任务和 Agent 运行均保留 `tenant_id` 扩展基础，不建设 SaaS 运营后台。
4. Local、CI/Test 和隔离 Staging 可以用于实现与验证；Internal 和 Customer Production 的部署、迁移、回填、真实数据写入及密钥配置始终需要明确授权。
5. Supabase/PostgreSQL 是工作站业务数据的权威源。
6. 飞书是身份、通讯录和任务消息通知的权威外部系统。
7. 审批在 QuantXY 内执行和审计，飞书只发送待办与结果通知。
8. 请假和考勤不属于本次范围；正式导航、快速创建和直接路由全部隐藏，历史数据库结构和代码保留。
9. 正式模式禁止 mock、seed、fixture 和业务 localStorage 回退。Local 仅可使用合成数据，但必须经过真实适配器和持久化路径，不能以 formal mock fallback 冒充成功；生产数据永不进入 Local、CI/Test 或普通 Staging。
10. 桌面端与移动端使用同一套 Next.js 领域与权限逻辑；移动端交付为可安装 PWA，并采用独立的移动 App 交互，不是桌面页面缩放。

## 2. 范围

### 2.1 纳入范围

- 正式入口、身份认证、Session、RBAC、RLS、审计和租户隔离
- 组织、部门、岗位、职级、员工目录、飞书通讯录同步、工作画像和技能
- 决策驾驶舱、部门工作台、员工执行台、财务中心、HR 中心
- 项目、项目成员、预算、里程碑、风险、活动、日报、任务、评论、依赖和文件
- 客户、联系人、商机、跟进和项目交付关联
- 审批、报账、附件、财务处理和状态审计
- 薪资批次、锁定、发布/撤回、发薪快照、本人查询和受控导出
- 知识目录、文档、版本、权限、检索、引用和来源追踪
- AI 助理、会话、消息、工具调用、模型配置、用量和限流
- AI 调度目标、方案、人工改派、确认下发和成本依据
- Agent 定义、版本、权限、申请、调用、编排和执行日志
- 数据分析、通知中心、企业设置、个人设置和操作监控
- 页面上下文驱动的快速创建菜单
- 专业桌面端可视化、响应式移动端和可安装 PWA
- 数据库迁移、真实数据库测试、浏览器 E2E、Staging 验收、备份恢复和发布门禁

### 2.2 仅保留未来租户扩展基础

- 业务表、审计、Storage 路径、缓存键、向量索引、通知、定时任务和 Agent 运行显式携带 `tenant_id`；服务器查询显式建立 tenant 上下文。
- 企业名称、Logo、时区和基础设置写入配置表；不得硬编码当前客户名称、企业 ID、部门结构或品牌。
- 本期只配置并运营一个正式企业租户；不提供跨租户运营界面或运营流程。

### 2.3 Deferred（不进入本次商业发布门禁）

- 请假业务流程
- 考勤查询和打卡
- 微服务拆分、原生 iOS/Android App、复杂离线业务编辑
- 平台运营总后台、企业自助注册/自动开通向导、套餐和在线计费、在线支付、模板市场/完整行业模板中心
- 多客户续费管理、多客户统一用量运营中心、自动白标、自定义域名自动开通、自动化独享部署、私有化部署管理平台和复杂跨租户运营
- 完整薪资核算引擎、通用可视化审批设计器、高级 Agent 间自主协作
- 未经明确授权的 Internal/Customer Production 部署、真实客户数据写入、生产迁移或数据回填

## 3. 总体架构

采用模块化单体架构：

```text
Browser
  -> Next.js Server Components / Client Components
    -> Next.js Route Handlers
      -> Session + permission + validation
        -> PostgreSQL transaction RPC / user-scoped Supabase client
          -> business tables + append-only audit + outbox
            -> Feishu / DeepSeek / Supabase Storage adapters
```

### 3.1 组件职责

- **Next.js 页面：** 展示服务器事实、收集输入、显示加载/无权限/无数据/失败状态。
- **Route Handler：** 认证、权限、请求验证、幂等键、错误映射和 request ID。
- **领域服务：** 业务规则、状态机、金额规则、并发控制和第三方适配器调用。
- **PostgreSQL RPC：** 多表事务、最终授权检查、状态转换和审计原子写入。
- **RLS：** 最后一道 tenant、organization、本人、参与人和管理权限隔离。
- **Outbox：** 外部消息与异步任务的持久化、重试和去重。
- **外部适配器：** 飞书、DeepSeek、Supabase Storage；外部错误不能伪装为业务成功。

### 3.2 数据归属

| 数据 | 权威系统 | QuantXY 责任 |
|---|---|---|
| 登录身份、飞书用户映射 | 飞书 + Supabase Auth | 建立和校验 workspace session |
| 通讯录、部门基础信息 | 飞书 | 同步快照、处理离职和组织变更、记录同步问题 |
| 项目、任务、客户、审批、报账、薪资 | QuantXY PostgreSQL | 完整业务状态与审计 |
| 知识文档元数据 | QuantXY PostgreSQL | 版本、权限、来源和检索索引 |
| 文件二进制 | Supabase Storage | 签名上传、病毒/类型检查、对象权限和生命周期 |
| AI 配置、会话、Agent、调度 | QuantXY PostgreSQL | 权限、调用记录、用量、方案版本和审计 |
| 飞书通知 | QuantXY Outbox + 飞书 | QuantXY 保留投递状态，飞书负责实际送达 |

### 3.3 桌面端与移动端产品形态

- 桌面端采用侧边导航、页面标题区、上下文操作区、可追溯指标卡、图表、数据表和详情抽屉。
- 移动端采用底部主导航、顶部页面标题、浮动主操作按钮、底部操作面板、卡片列表和分步表单。
- 移动端和桌面端共享同一份服务器数据、权限、状态机和快速创建注册表，不维护第二套业务实现。
- PWA 提供 manifest、图标、安装入口、启动页和版本更新提示。
- Service Worker 只缓存应用壳和公开静态资源；不缓存薪资、审批、报账、客户、Agent 输出等敏感响应。
- 离线时明确显示离线状态并禁用业务写操作，不在浏览器排队伪造成功。

## 4. 全局商用规则

### 4.1 身份与授权

- 客户端不得提交可信的 `tenantId`、`organizationId`、`actorId` 或代替他人的 member ID。
- tenant、organization 和 actor 必须从已验证 Session 解析。
- 页面隐藏不是授权；每个 Route Handler、RPC 和 RLS 都独立验证。
- 新增细粒度权限至少包括：
  - `ai.config.manage`
  - `organization.manage`
  - `role.manage`
  - `project.manage`
  - `task.manage`
  - `customer.manage`
  - `approval.submit`
  - `approval.act`
  - `expense.manage`
  - `salary.manage`
  - `knowledge.manage`
  - `agent.manage`
  - `agent.orchestrate`
  - `analytics.read`
  - `settings.manage`
- 普通员工只能读取自己的薪资、本人敏感资料、本人参与的审批和被授权的 Agent 输出。
- 员工、直属主管（supervisor）、部门负责人、HR、Finance、Admin/Owner 的范围必须明确；直属主管由 direct-manager mapping 决定，不使用 Owner 代替，也不使用“任何 active member”作为管理权限。

### 4.2 数据隔离

- 所有租户业务表包含 tenant 和 organization 归属或有可证明的父级复合外键。
- 所有租户业务表启用 RLS；除有书面理由的全局字典外启用 FORCE RLS。
- service-role 仅用于后台同步、外部投递和受控管理 RPC；每次查询必须显式绑定 tenant 和 organization。
- 员工公开目录与 HR 私密资料分离，电话、私人邮箱、入离职信息不对全组织整行开放。
- 审批只对申请人、当前或历史审批人，以及获授权的管理角色可见。

### 4.3 事务、幂等与并发

- 创建型接口接受 `Idempotency-Key`，数据库使用 tenant + operation + key 唯一约束。
- 项目及成员、批量任务、审批动作、工资确认、Agent 发布等多表写入在单个事务中完成。
- 状态机操作使用数据库版本号或 compare-and-swap；冲突返回 `409 conflict`。
- 已确认工资、已执行审批动作、审计日志和最终 Agent 执行记录不可由客户端修改或删除。

### 4.4 审计

所有业务写操作必须在同一事务中记录：

- tenant、organization、actor、权限上下文
- action、entity type、entity ID
- before、after 或安全摘要
- request ID、idempotency key
- 用户输入的业务理由或审批意见
- 成功或失败结果及稳定错误码

密钥、密码、完整 AI prompt、薪资明细和文件内容不得直接进入普通应用日志。

### 4.5 正式模式隔离

- 生产构建发现 demo/mock 启用时启动失败。
- 正式页面不读取 seed、fixture 或业务 localStorage。
- localStorage 仅允许保存无敏感信息的显示偏好。
- 可选查询失败必须返回模块错误；不得转换为“暂无数据”，不得调用 `seedAgents()` 等演示回退。
- 未完成真实接口的页面和操作在正式模式不可访问。

### 4.6 数据、存储、时间与金额的不可变规则

- 每张企业业务表必须有 `tenant_id`、`created_at`、`updated_at`、`created_by`、`updated_by`；需要并发编辑的实体同时有 `version` 乐观锁。
- 审计仅追加，普通管理员不可修改或删除；审批、工资与 Agent 运行保存不可变业务快照。
- 金额以固定精度 `Decimal`/数据库 `numeric` 存储与计算，禁止浮点数；时间以 UTC 存储，按企业时区显示。
- Storage 使用 `tenant/{tenantPublicId}/...` 路径与服务端签名 URL；缓存键、向量 namespace、outbox、队列和计划任务都带 tenant 维度。
- 所有业务数据定义归档、删除、保存期限与恢复规则。删除文件/知识资料必须清理关联对象和向量，并留下审计；不允许绕过 RLS 的浏览器 service role。

### 4.7 迁移与环境保护

- 环境固定为 Local、CI/Test、Staging、Internal、Customer Production，且数据库、Storage、飞书应用和 AI 密钥均隔离；Staging 只使用合成企业数据。
- 在 Plan02 首个可执行任务中建立唯一共享的 fail-closed environment/DB command guard；`db:reset:test`、DROP、TRUNCATE 与测试 seed 必须先识别环境，unknown、Internal 或 Customer Production 一律在建立连接前硬失败。后续计划只能消费该 guard，不能另建绕过或重复实现。
- 正式库只允许评审后的前向迁移。新增字段先允许 NULL 或提供安全默认值；回填必须可重复、可中断、分批、可观测，并有迁移前备份、dry run、数量/完整性验证和 rollback 或 forward-repair 方案。
- 所有迁移先在 Local 和 Staging 验证；未经明确授权不得在 Internal 或 Customer Production 执行。

## 5. 模块设计

### 5.1 正式入口与工作台

- Next.js server layout 读取 session、role codes、permission codes、job level 和 module capabilities。
- middleware 和 server layout 都执行直接 URL 权限检查。
- 工作台 KPI 必须来自数据库聚合或具备可追溯的计算公式。
- 移除固定截止日期、固定风险率、合成趋势和静态“AI 洞察”。
- 每个指标可追溯到查询时间、数据范围和源实体。

### 5.2 组织与员工

完整流程：

1. 管理员触发飞书目录同步。
2. 同步创建 snapshot 和 run，分页读取部门与员工。
3. 数据通过事务 RPC upsert；分页上限、缺失/重复 page token 或外部接口失败时整次同步回滚，不应用部分实体，也不移动上一份 complete 快照的成功标记。
4. 成功同步返回真实 run public ID 与计数；失败通过独立的 service-only 事务 RPC 持久化 failed run、脱敏 issue、audit 和 request ID，浏览器角色不得直写运行证据。
5. 离职、部门、岗位和职级变更产生审计与同步问题记录。
6. 管理员可以维护仅属于 QuantXY 的角色和权限；飞书来源字段只读。
7. 员工维护自己的工作画像；技能认证由授权管理者审核。

飞书 OAuth 登录、首次全量与增量同步均属于正式范围。Webhook 必须验证签名，使用事件 ID 幂等、乱序保护、同步游标、限流退避与重试；持久化失败记录并提供异常管理入口。定期全量对账处理部门移动、转岗、人员唯一映射及手工修改冲突。离职事件必须立即撤销 Session/权限与未完成访问授权；公开资料、私有 PII 和主管视图分别投影并审计。

验收：跨租户成员不可见；普通员工不可读取 HR 私密字段；所有角色变更有审计。

### 5.3 项目、活动、任务和文件

完整流程：

1. 有权限用户创建项目，事务内创建项目、负责人、成员关系和审计。
2. 项目支持编辑、归档、预算、日期、里程碑、风险和成员管理。
3. 活动与客户或项目关联，支持计划、负责人、阶段、跟进和复盘。
4. 任务支持单条和批量创建、依赖、评论、领取、进度、提交、验收、驳回和重开。
5. 日报和成果引用真实任务、项目和文件。
6. 文件使用签名上传；完成上传后服务端验证对象、类型、大小和归属，再创建 file relation。
7. 通知先写 outbox，再调用飞书；送达、失败、重试和 message ID 全部持久化。

验收：故障注入时不产生孤立项目或半批次任务；相同幂等键不会重复创建。

### 5.4 客户与交付

新增正式业务模型：客户、联系人、商机、客户活动和项目交付关联。

完整流程：

1. 创建客户并检查 tenant 内名称/统一社会信用代码重复。
2. 维护联系人和隐私可见范围。
3. 创建商机，维护阶段、金额、预计成交日和负责人。
4. 跟进记录不可伪造 actor 和时间。
5. 商机成交后可事务创建或关联项目。
6. 客户详情聚合项目、活动、文件和审批，但仍遵守各模块权限。

正式客户页不得读取 seed 或 localStorage。

### 5.5 审批与报账

审批使用 QuantXY 内部状态机，核心状态为 draft、pending、approved、rejected、cancelled。

完整流程：

1. 申请人从审批模板发起实例。
2. 事务创建 approval、steps、首个待办和审计。
3. 只有当前 pending step 的授权审批人可以同意、拒绝或退回。
4. 审批动作校验版本号并原子更新 step、approval、action 和 audit。
5. 非参与员工无法读取表单、金额、附件和意见。
6. 报账保存草稿、上传凭证、提交审批、审批完成、财务付款和归档。
7. requester、owner、project、approval 归属字段在提交后不可被客户端重写。
8. 飞书待办仅携带最少必要信息和 QuantXY 深链。

前端只有收到服务器成功响应并重新读取详情后，才显示审批成功。

### 5.6 薪资

完整流程：

1. Finance/HR 管理薪资政策和档位，政策按部门、岗位族、职级、层级和生效日期精确匹配。
2. 全公司政策允许 department 为空；数值解析必须区分 null 与 0。
3. 层级范围按数据库规则支持，不在浏览器压缩到 1–5。
4. 工资批次使用受控的薪资快照与导入/批准数据，不承诺计算税务或完整薪资规则引擎。
5. 锁定、发布或撤回时再次校验快照、版本和权限；已发布工资记录不可由普通用户修改。
6. 普通员工 bootstrap 只返回本人薪资；薪资管理员使用独立受控查询查看授权范围。

验收必须包含普通员工响应中不存在其他人的 salary band、工资或政策金额。

本期仅交付工资批次的锁定、发布/撤回、发薪快照、本人查看、财务/管理员审计与加密水印导出；不建设完整薪资计算引擎。

### 5.7 知识库

完整流程：

1. 创建目录并配置成员、部门或角色权限。
2. 通过 Storage 上传文档，创建 draft 版本和文件摘要。
3. 发布产生不可覆盖的版本；旧版本可追溯。
4. 检索只返回当前用户有权读取的版本。
5. AI 回答必须记录 document ID、version ID 和引用片段位置。
6. 删除采用归档和保留策略，不直接破坏审计链。

上传需执行哈希、类型/大小限制、隔离/安全扫描状态和版本关联；OCR/解析、向量索引、重建索引与过期资料标记均需可观测。搜索、下载和 AI 访问必须审计，AI 引用要包含来源版本与片段。企业知识默认不得用于第三方模型训练。

### 5.8 AI 配置与 AI 助理

- AI 配置 PUT 仅允许 `ai.config.manage`，密钥只在服务端加密保存，响应只返回 configured 和 hint。
- 配置修改记录 actor、旧配置摘要和新配置摘要，不记录密钥。
- AI 调用使用共享限流存储，维度至少包含 tenant、user 和 operation。
- 会话和消息服务端持久化；用户只能读取自己的会话，管理审计只能读取脱敏元数据。
- 模型超时、鉴权失败、限流和结构错误返回稳定错误码。
- invocation 在调用前创建，成功、失败和超时均在 finally 路径收口。

- 对话、队列、调度、取消、重试、死信队列、并发锁、模型降级、Token/费用/并发预算、部门与用户配额、保存期限、评测集和失败后人工接管均为正式范围。
- 发送消息、修改业务数据、创建审批、发布内容、修改权限、删除资料、导出数据、创建付款相关记录这八类高风险操作，均须在执行前获取人工确认并写入确认与执行审计。

### 5.9 AI 调度

完整流程：

1. 用户创建调度目标和约束。
2. 服务端加载项目、成员、技能、当前任务和可用成本数据。
3. 模型生成版本化方案；模型失败时可生成明确标识的规则方案，但不能冒充模型结果。
4. 人工改派记录 AI 原推荐、修改人、理由、时间和方案版本。
5. 确认下发引用已锁定的方案版本，事务创建批量任务和审计。
6. 成本未配置时显示“未配置”，不得输出 0 元优化结论。
7. 风险数值必须来自可解释规则或真实模型结果，不使用固定百分比。

### 5.10 Agent 中心

完整流程：

1. `agent.manage` 用户创建定义和 draft 版本。
2. Agent 的 system prompt、模型、工具和数据范围全部由服务器版本决定。
3. 发布版本经过权限和配置校验，历史版本不可覆盖。
4. Agent 权限支持公司、部门、角色、成员和最低职级范围。
5. 调用前服务器按 session tenant/org、Agent 状态和权限求交集。
6. 申请权限产生真实 request 和审批记录。
7. 编排保存节点、边、输入输出契约和版本；运行引用固定版本。
8. invocation、execution logs、token、cost 和结果摘要只能由服务端追加。
9. 空表显示真实空态；查询失败显示 request ID；正式模式永不加载演示 Agent。

Agent 运行必须执行工具/数据白名单、单次 Token/费用预算、最大时间、步骤、递归深度和并发限制，支持取消、人工节点、补偿、循环检测、发布前评测与企业 Kill Switch；密钥只能引用不能显示。编排仅支持人工定义、受控发布的 DAG；高级自主多 Agent 协作 Deferred。

### 5.11 数据分析、通知和设置

- 分析指标来自数据库视图或受测试的聚合查询，显示统计口径和更新时间。
- 通知中心统一读取真实 outbox/notification 数据；已读状态服务器持久化。
- 企业设置、个人偏好、通知偏好、调度参数和模型参数服务端持久化并按权限隔离。
- 个人显示偏好可以本地缓存，但服务器设置是权威源。

## 6. 页面上下文快速创建

实现统一的 `contextualCreateActions` 注册表。每个 action 包含：页面匹配、权限、模块 capability、标签、图标、打开方式和目标命令。

| 页面 | 菜单项 |
|---|---|
| 决策驾驶舱 | 新建决策目标、发起 AI 调度 |
| 部门工作台 | 新建项目、新建任务、新建活动 |
| 员工执行台 | 新建日报、提交成果、发起报账 |
| 财务中心 | 新建报账、创建核算批次、新建薪资政策 |
| HR 中心 | 同步飞书通讯录、新增部门、新增岗位 |
| 项目列表 | 新建项目 |
| 项目详情 | 新建里程碑、新建任务、上传文件、新增风险 |
| 活动中心 | 新建活动、新建跟进 |
| 任务中心 | 新建任务、批量创建任务 |
| 人员中心 | 同步飞书、新增成员、新增部门、新增岗位 |
| 审批中心 | 发起审批、发起报账 |
| 客户中心 | 新建客户、新建联系人、新建商机、新建跟进 |
| 知识中心 | 上传文档、新建知识目录 |
| AI 助理 | 新建会话 |
| Agent 中心 | 新建 Agent、新建编排、申请调用权限 |

规则：

- action 必须同时满足页面、服务器权限和模块 capability。
- 页面没有可用 action 时不渲染“快速创建”。
- 客户端过滤只负责体验，目标 API/RPC 继续独立鉴权。
- 创建成功后刷新服务器数据并显示由服务器返回的实体 ID。
- 未完成真实命令的 action 不得进入注册表。

桌面端使用标题区下拉菜单。移动端使用右下角浮动创建按钮，点击后从底部弹出操作面板；两者消费同一份 `contextualCreateActions`，所以权限和页面映射保持一致。

## 7. 专业可视化与移动 PWA 交互

### 7.1 响应式层级

- 桌面：`>= 1200px`，完整侧边导航、双栏或三栏工作区。
- 平板：`768px–1199px`，折叠导航、单栏主内容和详情抽屉。
- 手机：`< 768px`，底部导航、卡片列表、全屏详情和底部操作面板。
- 必须覆盖宽度 `360`、`375`、`390`、`430`、`768`、`1024`、`1366`、`1440`、`1920`；同时验收 iPhone Safari、Android Chrome、飞书/微信内置浏览器、Windows Chrome/Edge 与 macOS Safari/Chrome。Playwright viewport 不能替代最终真机验收。

### 7.2 移动端 App 逻辑

- 底部导航最多展示五个当前角色最常用入口，其余入口进入“更多”。
- 页面返回遵循列表 -> 详情 -> 编辑的层级；有未保存输入时必须二次确认。
- 表单按业务步骤拆分，固定底部提交栏避开系统安全区域。
- 主要触控目标不小于 `44x44px`，不依赖 hover 操作。
- 长表格在移动端转换为摘要卡片和详情页；确需对比的表格才允许横向滚动。
- 图表在小屏减少维度和标注，但数据口径与桌面端完全一致。
- 加载使用骨架屏；空数据、无权限、接口失败和离线状态必须视觉区分。
- 成功提示必须来自服务器响应；关键操作同时显示可追踪的实体状态。
- 薪资、审批、报账和密钥操作禁止在通知预览、浏览器缓存或后台页面暴露敏感正文。

### 7.3 视觉与可访问性

- 建立统一 design tokens：颜色、字体、间距、圆角、阴影、图标和状态色。
- 图表和状态不能只依赖颜色表达；正文与控件达到 WCAG 2.1 AA 对比度。
- 支持键盘导航、可见焦点、语义标题、表单标签和屏幕阅读器名称。
- 页面布局不使用固定业务数字填充视觉效果，所有可视化都来自真实数据或明确空态。
- Staging 目标：主要移动流程 P95 可交互时间不高于 3 秒，并对低端移动设备、弱网、断网、上传恢复、键盘、触控、安全区和基础无障碍做验证。

## 8. 错误处理与可观测性

统一错误结构：

```json
{
  "error": {
    "code": "approval_version_conflict",
    "message": "审批状态已变化，请刷新后重试",
    "requestId": "uuid"
  }
}
```

- `400`：验证错误
- `401`：未登录或 Session 失效
- `403`：权限不足
- `404`：实体不存在或不可见，避免跨租户枚举
- `409`：版本、状态或幂等冲突
- `422`：业务规则不满足
- `429`：共享限流触发
- `503`：数据库、飞书、模型或 Storage 暂不可用

生产日志使用结构化 JSON，包含 request ID、tenant public ID、route、duration、stable code，不输出密钥和敏感正文。监控至少覆盖错误率、P95、数据库连接、通知失败、AI 调用失败、审计写失败、备份失败和同步失败。

## 9. 测试与验收门禁

### 9.1 单元测试

- 业务状态机、权限匹配、金额规则、字段转换和错误映射
- 快速创建页面映射和权限过滤
- 正式模式不允许 demo fallback
- 桌面下拉和移动底部面板消费相同 action 注册表

### 9.2 API 集成测试

- 真实 Route Handler 与 session 上下文
- 请求体伪造 actor/tenant/org 无效
- 幂等、并发、错误码和审计调用
- 普通用户对敏感 API 得到 403 或 404

### 9.3 数据库测试

从空库执行全部 migration，并用至少两个 tenant、六类角色验证：

- RLS 与 FORCE RLS
- 薪资、审批、报账、员工 PII、知识和 Agent 隔离
- 审计不可修改
- 状态机事务、并发和失败回滚
- 外键、索引、唯一约束和幂等键

### 9.4 浏览器 E2E

不得拦截业务 API，必须真实验证：

- 创建 -> 刷新 -> 换浏览器 -> 另一角色读取
- 直接 URL、RSC 和 API 越权
- 项目、任务、客户、审批、报账、薪资、知识和 Agent 主流程
- 飞书通知 outbox 状态
- 快速创建只显示当前页面且有权限的 action
- 清空 localStorage 后业务状态不丢失
- 四类目标视口均无关键内容溢出；移动端底部导航、返回、浮动创建和分步表单符合 App 层级
- PWA 可安装、更新提示正常，Service Worker 不缓存敏感 API 响应

### 9.5 Staging 验收

- 独立 Supabase project、service key、AI 主密钥和飞书测试应用
- 完整 migration hash 与生产候选版本一致
- 真实飞书目录同步和消息送达
- 真实 DeepSeek 测试额度、超时、限流和密钥轮换
- Storage 上传、下载、授权和恶意类型拒绝
- 每日备份、PITR 与恢复到临时库演练
- TLS、安全头、WAF/共享限流、容器只读和 readiness
- 移动端性能、可访问性、弱网和真实设备触控验收

### 9.6 商业容量、恢复与最终命令门禁

- 验收容量为约 100 名员工、50 名同时活跃用户、20 个并发业务写入、10 个并发 AI/Agent 排队任务；目标负载下非 AI API P95 `<=800ms`、主要移动流程 P95 可交互 `<=3s`、非 AI API 错误率 `<0.5%`。
- 初期 RPO `<=24h`、RTO `<=4h`；Internal 试用前必须完成一次备份恢复演练。AI 不可用时项目、任务、CRM 和审批仍可使用。
- 适用门禁依次运行 `npm run test:unit`、`npm run test:coverage`、`npm run typecheck`、`npm run lint`、`npm run build`、`npm run test:security`、`npm run test:rls`、`npm run test:e2e`、`npm audit --omit=dev`、`git diff --check`；仅在需验证干净安装时运行 `npm ci`。
- 数据库门禁为 `npm run db:reset:test`、`npm run db:migrate:dry-run`、`npm run db:test`、`npm run db:seed:validate`、`npm run db:rollback:test`。`verify:commercial:local` 覆盖 clean install、typecheck、lint、生产 build、unit/coverage、pgTAP/RLS 拒绝、集成、桌面/模拟移动 E2E、a11y、依赖/secret scan、迁移 dry-run 与负载 harness；授权的 `verify:commercial:staging` 覆盖 Staging smoke、OAuth/Webhook、Storage、安全、备份恢复、canary 与真机。最终 `verify:commercial` 必须验证与候选 commit 匹配的签名/哈希证据、RPO/RTO 和 release artifact manifest；缺少 Staging/恢复/canary/真机证据时必须 BLOCKED。

## 10. 迁移与发布策略

1. 保留当前未提交 WIP，先修复薪资匹配和隐私问题。
2. 建立正式 module capability 和权限注册表。
3. 按模块把 fused 中的真实流程迁入 Next.js。
4. 每迁一个模块，同时删除对应 Next fixture/localStorage 分支。
5. fused 在迁移期保持不可新增功能；仅当新版本功能对等、数据验证通过、Staging 灰度成功、回滚路径确认且获得明确授权时才可删除。历史数据库可保留。
6. 请假和考勤从正式 navigation、role routes、快速创建和直接路由中移除。
7. 所有模块完成后执行全量五层门禁和 Staging 验收。
8. 只有验收报告无 P0/P1、恢复演练通过且用户明确授权时，才生成生产发布操作。

## 12. 完成定义

本项目只有同时满足以下条件才称为“可上线”：

- 纳入范围的所有模块均使用真实接口和服务器持久化。
- 正式构建不包含可触达的 mock、seed、fixture 或业务 localStorage 分支。
- P0/P1 安全与数据完整性问题清零。
- 单元、HTML、类型、lint、build、数据库、API 集成和浏览器 E2E 全部通过。
- 飞书、DeepSeek、Storage 在 Staging 有真实成功与失败证据。
- 备份恢复演练、告警、日志脱敏和安全配置有书面证据。
- fused 正式入口只在功能对等、数据验证、Staging canary、可验证回滚和明确授权均有签名/哈希证据后下线；缺任何一项则保留迁移资产并处于 BLOCKED。
- 桌面端与移动 PWA 在目标视口、真实设备、性能和可访问性门禁中通过。
- 用户明确批准生产发布。
