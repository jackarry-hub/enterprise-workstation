# QuantXY 个人执行工作台与个人薪酬中心设计

## 目标

在现有 `quantxy-ai-workbench-fused.html` 单页工作站上增量补齐“个人接收任务、执行、提交成果、验收、完成”的闭环，并把财务中心从企业经营看板改为跟随当前身份的个人工资与奖金中心。

本次只改造现有演示版的数据和交互，不重做技术架构，不接入数据库，不增加考勤或请假功能。项目、客户、AI 调度、知识库和 Agent 等既有模块继续保留。

## 已确认的产品原则

1. 右上角切换到哪个身份，个人工作台、个人任务、个人项目和个人薪酬就展示哪个身份的数据。
2. 个人工作台不混入其他成员的任务和薪酬。
3. 所有统计卡片、任务、项目、工资和奖金数据必须有明确的点击结果，不能只改变鼠标样式。
4. 演示数据保存在当前浏览器，刷新页面后保留；“重置演示数据”可恢复初始数据。
5. 不依赖 Supabase，不新增数据库，不增加真实多人协作能力。
6. 不增加传统考勤、请假和全员工资管理页面。

## 选定方案

采用现有单文件状态模型和事件代理机制进行增量扩展：

- 继续以 `S.me` 作为当前身份。
- 扩展现有任务对象，补充发起人、验收人、执行反馈、成果和时间线字段。
- 新增个人薪酬演示数据，并按成员 ID 隔离读取。
- 继续通过 `data-act` 统一处理点击行为。
- 继续使用现有浏览器存储机制保存演示状态。
- 在根目录和 `public` 目录同步维护两份融合 HTML，保证本地预览与 Next.js 部署内容一致。

没有选择照搬参考站的页面结构或重新开发 React 页面，因为当前融合工作站已经具有成熟的导航、状态、样式和事件体系；增量扩展能降低对既有功能的影响。

## 信息架构

### 个人工作台

保留侧边栏“员工工作台”入口，页面内容重组为以下区域：

1. **个人欢迎与执行摘要**
   - 当前身份、岗位和部门。
   - 待处理、进行中、待验收、已逾期数量。
   - 每个数量均可点击并进入对应任务筛选。

2. **今日必须处理**
   - 只展示与当前身份相关且未完成的任务。
   - 排序优先级依次为：已逾期、存在阻塞、待验收、P0、临近截止日期。
   - 点击任务进入个人执行详情。

3. **我的任务**
   - 提供“我的待办”和“我发起的”两个范围。
   - 提供待处理、进行中、待验收、已完成、已逾期筛选。
   - 列表行整体可点击，独立操作按钮不会误触发整行跳转。

4. **我的项目**
   - 展示当前身份负责或参与的项目。
   - 点击项目进入现有项目详情。

5. **个人收入**
   - 展示最近月份实发工资、绩效奖金和项目奖金。
   - 点击卡片进入当前月份的个人薪酬明细。

6. **执行提醒**
   - 根据任务截止日期、阻塞状态、待验收状态生成演示提醒。
   - 点击提醒进入关联任务。

### 个人执行详情

新增单页内部路由 `execution`，复用现有 `S.sel.task` 选中任务。所有任务入口统一跳转到该详情，避免不同页面出现不一致的任务操作逻辑。

详情包含：

- 任务名称、所属项目、优先级、状态和截止日期。
- 任务说明与验收标准。
- 发起人、执行人和验收人。
- 当前进度、阻塞原因和下一步计划。
- 成果说明、成果链接和文件名称列表。
- 按时间倒序展示的执行记录。
- 与当前身份和任务状态相匹配的操作按钮。

## 任务执行闭环

### 状态定义

- `待处理`：任务已分配，执行人尚未领取。
- `进行中`：执行人已领取并开始执行。
- `待验收`：执行人已提交成果，等待验收人处理。
- `已完成`：成果已验收通过。
- `已逾期`：不作为持久化状态；当任务未完成且截止日期早于今天时动态计算。

现有 `待审核` 数据在载入时迁移为 `待验收`，避免同一流程出现两套名称。

### 操作权限

当前身份以 `S.me` 为准：

- 只有任务执行人可以领取任务、更新进度、填写阻塞、补充成果并提交验收。
- 只有任务发起人或明确指定的验收人可以通过或驳回成果。
- 已完成任务默认只读；重新打开后回到 `进行中`，并写入执行记录。
- 右上角身份切换属于演示能力，切换后立即按新身份重新计算可见数据和可用操作。

### 流程

```text
待处理
  → 执行人领取
进行中
  → 更新进度、阻塞、下一步计划
  → 填写成果说明，添加成果链接或文件名称
  → 提交验收
待验收
  → 验收人通过 → 已完成
  → 验收人驳回 → 进行中
```

每次状态变化都追加一条时间线记录，至少包含操作者、动作、时间和备注。演示版不保存真实文件，只保存用户选择或填写的文件名称与成果链接。

## 任务数据扩展

在兼容现有字段的基础上增加：

- `createdBy`：任务发起人成员 ID。
- `reviewer`：成果验收人成员 ID。
- `description`：任务说明。
- `ac`：验收标准，沿用现有字段。
- `pr`：执行进度，范围 0–100。
- `blocker`：当前阻塞原因。
- `nextStep`：下一步计划。
- `resultText`：成果说明。
- `resultLink`：成果链接。
- `resultFiles`：成果文件名称数组。
- `acceptedAt`：领取时间。
- `submittedAt`：最近提交验收时间。
- `reviewedAt`：最近验收时间。
- `reviewNote`：验收意见。
- `timeline`：执行记录数组。

旧浏览器数据缺少这些字段时，由数据迁移函数补齐安全默认值，不清空用户已有任务。

## 个人薪酬中心

### 页面定位

侧边栏继续使用“财务中心”入口，但页面含义改为“我的薪酬”。不再显示企业营业收入、利润率、现金流、预算执行和全公司工资表。

### 薪酬字段

每个成员按月份拥有独立演示记录：

- 基本工资。
- 绩效奖金。
- 项目奖金。
- 其他奖励。
- 社保公积金扣款。
- 个人所得税。
- 其他扣款。
- 应发工资。
- 扣款合计。
- 实发工资。
- 发放状态和发放日期。

计算关系固定为：

```text
应发工资 = 基本工资 + 绩效奖金 + 项目奖金 + 其他奖励
扣款合计 = 社保公积金扣款 + 个人所得税 + 其他扣款
实发工资 = 应发工资 - 扣款合计
```

### 隐私边界

- 财务中心只从当前 `S.me` 对应的薪酬记录中取数。
- 身份切换后清除已选择的月份详情，再载入新身份的数据。
- 页面不提供全员工资列表、横向薪资对比或公司工资汇总。
- 搜索结果不包含其他成员的薪酬信息。

### 点击行为

- 实发工资卡片进入当前月份完整工资条。
- 绩效奖金卡片定位到奖金构成。
- 项目奖金卡片定位到项目奖金构成。
- 月份记录整行可点击并切换工资条详情。
- 没有薪酬数据时显示明确空状态，不生成其他身份的替代数据。

## 点击交互约束

所有带悬停、阴影、箭头、链接样式或手型光标的元素必须满足以下之一：

1. 通过 `data-act` 触发页面跳转、筛选或业务动作。
2. 是表单输入控件并能更新当前状态。
3. 明确显示为禁用状态，并说明禁用原因。

具体映射：

- 工作台任务数量 → 任务中心对应范围和状态筛选。
- 今日必须处理、执行提醒、任务列表 → 个人执行详情。
- 我的项目卡片 → 现有项目详情。
- 个人收入卡片 → 财务中心对应月份和明细区。
- 工资月份行 → 该月工资条。
- 状态按钮 → 完成相应任务闭环动作并追加时间线。

## 本地持久化与重置

- 任务扩展数据、薪酬演示数据、当前筛选和详情选择继续保存在当前浏览器。
- 不保存真实 API Key、登录密码或其他服务端秘密。
- “重置演示数据”同时恢复任务闭环数据和个人薪酬种子数据。
- 载入旧版本浏览器数据时执行非破坏性迁移；只补充缺失字段，不覆盖用户已有执行内容。
- 身份切换只改变视图范围，不复制或移动数据。

## 异常和边界处理

- 任务已被删除或 ID 无效时，返回个人任务列表并提示任务不存在。
- 当前身份不是执行人时，不显示执行人操作按钮。
- 当前身份不是验收人或发起人时，不显示验收按钮。
- 提交验收前必须填写成果说明；成果链接和文件名称至少填写一种。
- 驳回时必须填写验收意见。
- 进度必须限制在 0–100。
- 薪酬记录中的计算字段以明细重新计算，避免种子数据合计不一致。
- 缺少月份数据时保持个人数据边界，不回退到企业财务示例。

## 与现有模块的关系

- AI 调度下发任务时自动写入 `createdBy`、`reviewer` 和初始时间线。
- 手工创建任务时以当前身份作为 `createdBy`，执行人来自表单指派。
- 项目详情中的任务点击统一进入个人执行详情。
- 任务中心继续承担全量任务查看和筛选，但个人工作台只显示与当前身份相关的数据。
- 企业决策人身份的个人工作台不再自动混入全团队待审核任务；团队级审批仍留在现有业务决策中心。
- 财务中心不读取或修改现有项目预算字段。

## 测试与验收

### 数据与逻辑测试

- 旧任务数据可迁移，现有任务不丢失。
- 任务状态只能按规定路径变化。
- 非执行人不能领取或提交任务。
- 非验收人不能通过或驳回成果。
- 逾期由截止日期动态计算。
- 薪酬公式计算正确。
- 切换身份后看不到上一身份的任务详情和薪酬明细。
- 重置演示数据后任务和薪酬恢复种子状态。

### 浏览器验收

至少验证以下完整路径：

1. 登录工作站，进入员工工作台。
2. 切换到有待处理任务的成员并领取任务。
3. 更新进度和阻塞信息。
4. 填写成果并提交验收。
5. 切换到验收人，驳回一次，再由执行人修改后重新提交并通过。
6. 切换多个身份，确认工作台和财务数据同步变化且互不串数据。
7. 点击所有数字卡片、任务、项目、工资和奖金入口，确认都有可见结果。
8. 刷新页面，确认执行记录和薪酬选择状态符合设计。
9. 验证 AI 调度、项目、客户、知识库和 Agent 页面仍能打开。

### 部署验收

- 本地生产构建通过，不跳过 TypeScript 或测试错误。
- 根目录与 `public` 目录中的融合 HTML 保持一致。
- Git 工作区只包含本次功能相关修改。
- 推送 GitHub 后，服务器只更新 `ai-brain-demo` 项目。
- 重新构建后通过 `http://127.0.0.1:3010` 和公网 3010 页面验证。
- 不修改或影响服务器上的 `quantumgalaxy`、80、443、Nginx、Caddy、Redis 或 PostgreSQL。

## 明确不做

- 不接入 Supabase 或其他数据库。
- 不实现真实多用户并发和跨浏览器同步。
- 不上传或存储真实成果文件。
- 不增加考勤、请假、排班或全员工资管理。
- 不重做登录系统、AI 密钥后端或服务器基础设施。
- 不复制参考站的视觉样式，只借鉴个人执行闭环和信息组织逻辑。

## 完成标准

当任意演示身份都能看到自己的工作台数据，完成任务领取到验收的完整闭环，查看只属于自己的工资奖金明细，并且所有可点击数据都有确定行为，同时既有核心模块和部署隔离保持正常，本次改造即完成。
