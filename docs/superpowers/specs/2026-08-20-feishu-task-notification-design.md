# 飞书任务通知与工作台领取设计

## 目标

当有任务在正式工作站中创建并指派给员工后，企业工作站机器人立即向该员工发送飞书任务通知。员工点击通知中的“查看并领取”进入对应任务，必要时先完成飞书登录，再由本人确认领取并开始执行。

本阶段只实现任务指派通知和工作台领取，不实现飞书卡片内直接修改任务状态，不新增考勤、请假或其他审批流程。

## 已确认的产品决策

- 采用“飞书通知跳转工作台后领取”，不采用飞书卡片回调直接领取。
- 飞书消息不携带登录令牌、工资数据、内部数据库 ID 或其他秘密。
- 点击通知只打开任务，不通过 GET 请求自动改变任务状态。
- 员工仍需在工作台点击“领取任务”；现有服务端权限校验继续保证只有任务执行人可以领取。
- 正式访问地址来自 `NEXT_PUBLIC_APP_URL`，代码不得写死 `localhost`、服务器 IP 或端口。
- 当前使用既有 Supabase，不引入第二套数据库。

## 飞书应用配置

应用：`企业工作站`（`cli_aaf8636226791be9`）。

最小配置为：

1. 启用机器人能力。
2. 开通应用身份权限 `im:message:send_as_bot`。
3. 保留现有通讯录读取权限和“全部成员”数据范围，用于同步员工 `open_id`。
4. 应用发布时将可用范围覆盖实际使用工作站的员工。
5. 本方案不订阅消息事件，不配置卡片交互回调，也不要求公网回调地址。

机器人能力和消息权限只有在飞书创建并发布新版本后才对员工生效。权限配置与代码部署可以先完成，最终发布放在端到端验证之后。

## 架构

### 1. 通知队列

在现有 Supabase 中增加 `task_notifications` 表，只记录任务通知的投递状态：

- `task_id`
- `recipient_member_id`
- `event_type`，本阶段固定为 `task.assigned`
- `status`：`pending`、`sent`、`failed`
- `attempt_count`
- `feishu_message_id`
- `last_error_code`
- `created_at`、`last_attempt_at`、`sent_at`

表中不保存 `tenant_access_token`、App Secret 或完整飞书响应。任务创建事务通过数据库触发器写入唯一的待发送记录，避免任务已创建但通知记录丢失。唯一键防止同一任务、接收人和事件被重复排队。

### 2. 服务端通知模块

新增独立的飞书任务通知模块，负责：

- 从服务器环境变量读取 `FEISHU_APP_ID`、`FEISHU_APP_SECRET` 和 `NEXT_PUBLIC_APP_URL`。
- 使用 App ID 与 App Secret 换取短期 `tenant_access_token`。
- 只在服务器端解析任务执行人的飞书 `open_id`。
- 构造任务通知消息并调用飞书发送消息接口。
- 将飞书 `message_id` 或稳定的错误代码写回 `task_notifications`。

数据库上下文查询使用服务端专用 Supabase 客户端，并同时限定租户、组织、任务和接收成员。`open_id`、App Secret、访问令牌和飞书原始错误不得进入浏览器响应或应用日志。

### 3. 任务创建接口

现有 `POST /api/workstation/tasks` 保持先创建任务。数据库提交成功后，接口同步尝试发送飞书通知：

- 发送成功：返回任务和 `notification.status = "sent"`。
- 飞书暂时失败：任务仍然创建成功，返回 `notification.status = "failed"`，前端提示“任务已创建，飞书通知暂未送达”。
- 员工没有有效飞书身份：返回 `notification.status = "unavailable"`，提示管理员先同步通讯录。

飞书故障不得回滚已经创建的任务，也不得让前端误以为任务创建失败。

### 4. 重试接口

增加管理权限保护的 `POST /api/workstation/tasks/:taskId/notify`：

- 仅 `task.manage` 用户可调用。
- 只允许重发当前租户、当前组织内的任务指派通知。
- 通过唯一通知记录和投递状态避免无意重复发送。
- 每次尝试都递增 `attempt_count`，但不向前端暴露飞书令牌或 `open_id`。

正式工作台在通知失败时向有管理权限的用户显示一个简洁的“重发飞书通知”动作；普通员工不显示该动作。

## 飞书消息内容

消息应包含：

- 标题：`你有一项新任务`
- 任务名称
- 所属项目
- 发布人
- 优先级
- 截止日期
- 验收标准摘要
- “查看并领取”链接

链接格式为：

```text
${NEXT_PUBLIC_APP_URL}/quantxy-ai-workbench-fused.html?formal=1&task=<task-public-id>
```

只使用任务公开 UUID。不得使用数据库自增 ID、员工 `open_id`、访问令牌或敏感查询参数。

## 深链和登录返回

正式 HTML 工作站启动时读取 `task` 参数：

1. 参数必须是合法 UUID，否则忽略。
2. 未登录时，现有登录跳转把完整站内路径保存为安全的 `next` 参数。
3. 飞书登录完成后返回原始任务深链。
4. 服务端 bootstrap 完成后，仅当当前员工有权查看该任务时打开任务执行详情。
5. 无权查看或任务不存在时回到个人工作台并显示通用提示，不泄露任务内容。

领取仍调用既有 `PATCH /api/workstation/tasks/:taskId`，动作是 `claim`。服务端继续验证当前登录成员就是任务执行人，并通过状态条件避免重复领取。

## 安全边界

- `FEISHU_APP_SECRET` 和 `tenant_access_token` 只存在于服务器内存。
- `SUPABASE_SERVICE_ROLE_KEY` 只供通知上下文读取和投递状态更新使用，不进入客户端 bundle。
- 所有通知查询必须带租户和组织条件。
- App URL 只接受 `http:` 或 `https:`；生产环境建议使用 HTTPS 域名。
- 飞书原始错误只映射为稳定错误代码，例如 `token_unavailable`、`recipient_unavailable`、`send_failed`。
- 通知发送设置请求超时，避免飞书故障长期占用任务创建请求。
- 不配置卡片回调，因此不需要接收或验证飞书事件签名。

## 部署配置

服务器 `.env.production` 继续使用：

```text
NEXT_PUBLIC_APP_URL=https://最终工作站域名
FEISHU_APP_ID=服务器真实值
FEISHU_APP_SECRET=服务器真实值
SUPABASE_SERVICE_ROLE_KEY=服务器真实值
```

如果暂时继续使用服务器 IP，可将 `NEXT_PUBLIC_APP_URL` 配置为实际可访问的 `http://<server-ip>:3010`。正式多人使用前建议配置 HTTPS 域名；后续换域名只修改环境变量并重新构建，不修改业务代码。

## 错误处理与可观察性

- 任务创建和通知投递分别报告状态。
- 服务端日志只记录任务公开 ID、通知记录 ID、稳定错误代码和尝试次数。
- 不记录消息正文、`open_id`、App Secret、访问令牌或飞书完整响应。
- 失败通知保留在现有数据库中，便于管理员重试和后续增加定时补偿任务。

## 测试要求

1. 单元测试覆盖环境变量校验、深链生成、`open_id` 解析、飞书成功/失败响应和秘密脱敏。
2. 接口测试覆盖任务创建成功但通知失败仍返回 `201`、无管理权限禁止重试、重复重试不会重复排队。
3. HTML 行为测试覆盖合法任务深链、非法参数、登录返回和无权任务处理。
4. 数据库测试覆盖触发器、唯一键、租户隔离和通知状态迁移。
5. 本地使用模拟飞书响应完成端到端测试，不向真实员工发送测试消息。
6. 发布前使用一个明确指定的测试账号发送一条真实通知，确认飞书消息、登录返回、任务详情和领取操作全部贯通。

## 发布顺序

1. 本地实现并完成全部测试。
2. 推送代码和数据库 migration。
3. 在服务器部署新版本并配置正式 `NEXT_PUBLIC_APP_URL`。
4. 应用数据库 migration。
5. 使用测试员工验证一条真实任务通知。
6. 在飞书开发者后台创建并发布包含机器人能力与消息权限的新版本。
7. 扩大应用可用范围，让正式员工开始使用。
