# 企业工作站 Demo V1 任务执行反馈闭环设计

## 目标

在现有 `/projects/[id]` 项目详情任务 Tab 内补齐“任务发布 → 员工执行 → 状态更新 → 评论反馈 → 项目动态”闭环。继续使用 Mock 数据与现有浏览器项目仓库，不接入 Supabase、不增加新业务模块、不改变现有视觉体系。

## 范围

本阶段包含：

- 点击任务列表中的任务内容打开任务详情 Dialog。
- 展示任务名称、描述、负责人、截止时间、优先级和当前状态。
- 在任务详情中查看和添加评论。
- 记录创建任务、修改任务状态、添加任务评论三类项目动态。
- 使用统一 Mock User Context 提供当前操作人。
- 将任务、评论、动态和项目进度作为同一个 `ProjectDetailData` 聚合保存，刷新后继续保留。

本阶段不包含：

- Supabase 读写、登录认证和权限判断。
- 独立任务详情路由、任务中心联动、子任务、附件、@提及和消息通知。
- 新的活动类型数据库枚举或数据库 migration。
- 对其他业务模块和既有 UI 体系的修改。

## 方案选择

采用任务详情 Dialog 方案：任务仍属于项目上下文，用户无需离开任务 Tab 即可查看详情、更新状态和发表评论。相比新增侧边抽屉或 `/tasks/[id]` 路由，该方案直接复用现有 `Dialog`，变更面更小，桌面端与移动端行为也更一致。

## Mock User Context

新增统一入口 `src/lib/auth/mock-user.ts`，导出只读 `currentUser`：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定的 Mock 用户 ID |
| `name` | 当前演示用户姓名 |
| `role` | 当前演示用户角色 |
| `avatarUrl` | 可选头像地址 |

“李总”等具体演示身份只允许存在于 Mock User 适配层，任务业务组件、领域操作和动态文案都通过 `currentUser` 获取身份，不写死姓名。

未来接入 Supabase Auth 时，页面继续消费统一的当前用户对象；只将 Mock 适配层替换为服务端会话或 Auth Provider，不改变任务操作函数、评论模型与页面事件结构。

本阶段所有新操作统一以 `currentUser` 为操作人：

- 新任务的 `reporterId`。
- 任务状态动态的 `userId` 与显示姓名。
- 新评论的 `authorId`。
- 评论动态的 `userId` 与显示姓名。

已有历史评论仍通过项目成员目录解析作者；当前用户不属于项目成员时，由 Mock User Context 补充作者信息，不把当前用户伪造为项目成员。

## 数据模型与领域规则

继续复用现有模型：

- `ProjectTask`
- `TaskComment`
- `ProjectActivity`
- `ProjectDetailData`

不新增重复模型和临时数据库字段。

### 评论规则

- 评论内容必填，提交前去除首尾空格。
- 空白评论不写入数据，也不创建项目动态。
- 新评论生成稳定 ID、ISO 创建时间和更新时间。
- 新评论追加到 `detail.comments`，任务详情按创建时间正序展示，保证对话阅读顺序。
- 评论保存与对应项目动态采用一次不可变聚合更新，避免只保存其中一项。

### 项目动态规则

为保持既有 Schema 稳定，三类任务事件统一使用已有 `task_updated` 动作类型，由 `content` 区分业务语义：

- `{当前用户} 创建了任务「{任务名称}」`
- `{当前用户} 将任务「{任务名称}」更新为「{状态名称}」`
- `{当前用户} 评论了任务「{任务名称}」：{评论摘要}`

新动态插入 `detail.activities` 首位，使现有概览 Tab 的“最近项目操作记录”立即展示最新事件。评论动态摘要最多保留 48 个字符，超出后追加省略号；完整内容仍在任务详情中查看。

状态值未发生变化时不更新时间、不创建重复动态。找不到任务时返回原聚合。

### 项目进度

沿用现有规则：已完成任务数除以全部非取消任务数。添加评论不改变项目进度；创建任务和任务状态变化继续更新 `project.progress` 与 `project.updatedAt`。

## 页面与交互

### 任务列表

- 任务内容区域变为可点击入口，并提供清晰的 hover、键盘焦点和可访问名称。
- 状态选择控件保持列表内快速操作，点击或键盘操作状态控件不会误打开详情。
- 移动端整条任务卡片仍可自然堆叠，不产生横向滚动。

### 任务详情 Dialog

Dialog 使用选中任务 ID，而不是保存任务对象副本；状态更新后弹窗立即展示最新数据。

结构：

1. 标题区：任务名称、优先级 `StatusBadge`、当前状态。
2. 信息区：负责人 `Avatar`、截止日期、状态选择器。
3. 描述区：展示完整任务描述；无描述时使用克制的空状态文案。
4. 评论区：评论人头像、姓名、时间、正文。
5. 评论输入区：多行输入、发布按钮、校验反馈。

Dialog 桌面端采用中等宽度双层玻璃内容区，移动端限制在视口内并允许内容区域滚动；继续复用 `Dialog`、`Tabs`、`Avatar`、`StatusBadge`、`GlassCard`、`Select` 和 `Button`。

## 组件与数据流

- `ProjectTasksTab`：增加任务打开事件，仅负责列表展示和快速状态更新。
- `TaskDetailDialog`：新增任务详情与评论交互组件，不直接访问浏览器存储。
- `project-task-operations`：扩展纯函数，负责创建任务动态、状态动态和评论聚合更新。
- `ProjectDetailWorkspace`：持有选中任务 ID，统一注入 `currentUser`，保存每次聚合变更。
- `mock-project-repository`：继续保存完整 `ProjectDetailData`；不新增存储键和第二套状态容器。
- `ProjectOverviewTab`：不改变结构，直接消费更新后的 `detail.activities`。

数据流：

`currentUser + 用户操作 → 领域纯函数 → 新 ProjectDetailData → 单次保存 → Tasks/Overview/Dialog 同步刷新`

## 错误处理

- 空白评论：弹窗保持打开，显示“请输入评论内容”。
- 找不到选中任务：关闭详情 Dialog，不写入数据。
- 本地保存失败：不提交界面状态，显示保存失败反馈。
- 找不到历史评论作者：显示“未知成员”，但保留评论正文与时间。
- 取消任务保持不可修改状态，与当前任务 Tab 规则一致。

## 测试与验收

### 领域测试

- 创建任务使用 `currentUser.id` 作为发布人并生成项目动态。
- 状态变化生成一条包含操作者、任务和新状态的项目动态。
- 相同状态不生成重复动态。
- 有效评论同时写入 `TaskComment` 和 `ProjectActivity`。
- 空白评论被拒绝且聚合不变化。
- 评论不改变项目进度，任务状态仍按既有规则更新进度。

### 组件测试

- 点击任务内容打开详情，点击状态控件不误触打开。
- Dialog 展示六项任务信息。
- 历史评论正确解析项目成员和当前 Mock 用户。
- 发布评论后输入清空，新评论和时间立即显示。
- 在 Dialog 与列表中修改状态均保持一致。

### 浏览器验收

- 桌面端完成打开任务、添加评论、修改状态、查看概览动态的完整流程。
- 刷新页面后任务状态、评论和项目动态继续存在。
- 移动端 Dialog 无横向溢出，评论区可以滚动和提交。
- 项目进度与任务状态保持一致，浏览器控制台无错误。
- 输出任务详情和项目动态截图作为交付证据。

## 架构一致性

Mock User Context 是认证适配边界，不是新的业务用户模型。任务、评论和项目动态继续属于项目详情聚合，业务组件不读取全局硬编码姓名、不直接操作 `localStorage`。未来接入 Supabase 时，可将 `currentUser` 来源替换为真实会话，并将现有 Mock 仓库替换为数据访问层，而无需重写本阶段页面结构和业务动作。
