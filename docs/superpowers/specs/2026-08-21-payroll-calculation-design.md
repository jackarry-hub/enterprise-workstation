# 企业工作站 V1：薪资自动核算设计

## 1. 目标

把现有“手工录入扣款、展示工资结果”的薪资模块升级为可追溯的工资核算流程。财务或其他拥有 `salary.manage` 权限的人员录入收入和核算基础，系统在服务端计算社保、公积金、累计预扣个税、应发工资和实发工资；员工仍然只能查看本人记录。

本设计扩展 `2026-08-04-payroll-v09-design.md`。已有工资单继续可读，新核算只影响升级后创建或重新计算的记录。

## 2. 范围

### 包含

- 企业级、按生效月份版本化的社保及公积金个人缴费参数。
- 员工月度收入、缴费基数、税前扣除和年内累计期初数据录入。
- 居民个人工资薪金累计预扣法。
- 服务端预览、服务端最终计算、保存和历史快照。
- 应发、个人社保、公积金、个税、其他扣款、扣款合计和实发明细。
- 本人查看和薪资管理人员录入、复核的权限隔离。
- 桌面端和移动端工资单。

### 不包含

- 考勤、请假和缺勤扣款自动联动。
- 企业承担部分社保、公积金及完整用工成本。
- 个税申报、银行代发、会计凭证和税务机关接口。
- 非居民个人、劳务报酬、全年一次性奖金单独计税等特殊税务情形。

遇到不在本期范围内的员工，系统允许财务保留人工调整项，但必须填写原因；系统不声称替代专业财税申报软件。

## 3. 核算原则

### 3.1 收入与应发

```text
奖金合计 = 绩效奖金 + 项目奖金 + 其他奖励
应发工资 = 基本工资 + 奖金合计 + 其他应发
```

### 3.2 社保和公积金个人部分

企业为每个险种配置个人比例、缴费基数下限、缴费基数上限和生效月份。月度工资单录入员工社保基数和公积金基数。

```text
适用基数 = min(max(员工申报基数, 政策下限), 政策上限)
养老个人缴费 = 社保适用基数 × 养老个人比例
医疗个人缴费 = 社保适用基数 × 医疗个人比例 + 医疗个人固定额
失业个人缴费 = 社保适用基数 × 失业个人比例
公积金个人缴费 = 公积金适用基数 × 公积金个人比例
专项扣除合计 = 养老 + 医疗 + 失业 + 公积金
```

第一版不计算工伤、生育的员工个人扣款；如当地政策存在个人承担项，可通过版本化政策后续扩展，不混入“其他扣款”。

### 3.3 累计预扣个税

居民工资薪金使用国家税务总局公布的累计预扣法：

```text
累计应纳税所得额
= 累计收入
- 累计免税收入
- 累计减除费用
- 累计专项扣除
- 累计专项附加扣除
- 累计依法确定的其他扣除

累计应预扣税额
= max(0, 累计应纳税所得额 × 预扣率 - 速算扣除数 - 累计减免税额)

本期应预扣税额
= max(0, 累计应预扣税额 - 累计已预扣税额)
```

累计减除费用按 `5000 元 × 本年度截至当月在本单位任职受雇月份数` 计算。预扣率和速算扣除数使用居民工资薪金预扣率表。余额为负时当月不退税，年度汇算由税务流程处理。

参考依据：

- 国家税务总局《个人所得税扣缴申报管理办法（试行）》：<https://www.chinatax.gov.cn/chinatax/n810341/n810765/n3359382/201812/c4182700/content.html>
- 国家税务总局累计预扣法及预扣率表说明：<https://fgk.chinatax.gov.cn/zcfgk/c100015/c5200946/content.html>

### 3.4 最终金额

```text
扣款合计 = 专项扣除合计 + 本期个税 + 其他扣款
实发工资 = 应发工资 - 扣款合计
```

金额统一使用十进制定点数并按人民币“分”四舍五入。不得使用 JavaScript 浮点结果作为最终入库值。实发工资小于零时禁止确认。

## 4. 数据模型

### 4.1 `payroll_policies`

保存企业核算参数的版本：

- `organization_id`
- `effective_month`
- `pension_employee_rate`
- `medical_employee_rate`
- `medical_employee_fixed_amount`
- `unemployment_employee_rate`
- `housing_fund_employee_rate`
- `social_base_min` / `social_base_max`
- `housing_base_min` / `housing_base_max`
- `status`：`draft`、`active`、`retired`
- 创建人、确认人和时间戳

同一组织同一生效月份只能有一个有效版本。工资单按工资月份选择不晚于该月份的最近一个 `active` 版本。

### 4.2 `salary` 扩展

保留现有汇总字段，并增加：

- `policy_id` 和不可变的 `policy_snapshot jsonb`
- `other_income`
- `gross_salary`
- `social_base` / `housing_fund_base`
- `pension_employee`
- `medical_employee`
- `unemployment_employee`
- `housing_fund_employee`
- `tax_exempt_income`
- `special_additional_deduction`
- `other_statutory_deduction`
- `tax_relief`
- `employment_months_ytd`
- `opening_cumulative_income`
- `opening_cumulative_tax_exempt_income`
- `opening_cumulative_special_deduction`
- `opening_cumulative_special_additional_deduction`
- `opening_cumulative_other_statutory_deduction`
- `opening_cumulative_tax_relief`
- `opening_cumulative_tax_withheld`
- `cumulative_taxable_income`
- `individual_income_tax`
- `calculation_snapshot jsonb`
- `manual_adjustment_reason`
- `calculation_version`

`policy_snapshot` 和 `calculation_snapshot` 保存工资确认时的输入、公式版本、费率、税档和输出。后续修改企业政策不能改变历史工资单。

### 4.3 兼容策略

- 旧记录没有 `calculation_version` 时标记为“历史手工记录”，继续显示原汇总金额。
- 不自动重算旧记录。
- 现有 `social_security` 字段继续保存“个人社保与公积金扣款合计”，详细险种字段作为新计算来源，以兼容现有工作站读取逻辑。
- 现有 `bonus` 字段继续保存绩效、项目和其他奖励合计；`gross_salary` 保存包含其他应发后的完整应发工资。
- 对升级后的工资单，数据库中的汇总金额只能由服务端计算器生成。

## 5. 服务端结构

计算器拆为三个无副作用模块：

1. `resolvePayrollPolicy`：按组织和工资月份选择政策并验证基数范围。
2. `calculateCumulativeTax`：根据年内历史工资单、期初累计值和国家预扣率表计算本期个税。
3. `calculatePayroll`：汇总收入、专项扣除、个税、其他扣款和实发金额。

API 分两步：

- `POST /api/workstation/payroll/preview`：校验输入并返回计算明细，不落库。
- `POST /api/workstation/payroll`：重新执行相同计算后保存，忽略客户端提交的应发、个税、扣款合计和实发金额。

保存和历史累计读取必须在同一组织边界内执行。正式保存使用数据库事务或等效的原子 RPC，避免同一员工同一月份并发修改造成累计税额不一致。

## 6. 页面流程

### 6.1 企业核算参数

在“系统设置”增加“薪资核算参数”：

- 生效月份和各项个人费率。
- 社保、公积金基数上下限。
- 草稿保存、启用和查看历史版本。
- 启用前显示一组示例计算，要求授权人员确认。

没有有效政策时，不允许创建自动核算工资单。

### 6.2 薪资录入

薪资管理页按顺序显示：

1. 员工与月份。
2. 收入项目。
3. 社保、公积金基数。
4. 个税扣除项目和年中接入期初累计值。
5. 实时预览：应发、养老、医疗、失业、公积金、个税、其他扣款、实发。
6. “保存草稿”与“确认工资单”。

输入变化后调用预览接口。缺少参数时只提示缺失项，不显示一个看似有效的零值结果。

### 6.3 员工工资单

员工端继续保留简洁入口，工资单展示：

- 顶部：月份、应发、扣款合计、实发和状态。
- 收入明细。
- 养老、医疗、失业、公积金个人扣款明细。
- 累计计税基础、本期个税及公式说明。
- 其他扣款及原因。
- 最近月份记录。

移动端默认优先显示实发工资和扣款摘要，详细计算折叠展开。

## 7. 权限与隐私

- `payroll.read.self`：只读取当前登录成员关联员工档案的工资单。
- `salary.manage`：创建政策、预览、录入和确认工资单。
- 普通员工不能读取其他员工数据，也不能提交员工 ID 绕过边界。
- 任何工资保存、政策启用和人工调整均写入审计日志。
- 前端、日志和错误信息不得输出整份工资单或员工税务输入。

## 8. 错误处理

以下情况阻止确认：

- 工资月份没有有效政策。
- 基数、费率、收入或扣除不是有效非负金额。
- 年中接入时缺少期初累计值。
- 同一员工同一月份已经存在已确认工资单。
- 实发工资小于零。
- 历史月份缺失导致累计税额无法可靠计算。

草稿允许补充数据；第一版的已确认或已发放记录锁定且不能在线修改。线上更正版本不在本期范围内，避免在没有完整冲正审计链的情况下覆盖历史快照。

## 9. 测试与验收

### 计算单元测试

- 缴费基数低于下限、高于上限和处于区间内。
- 医疗固定额和比例组合。
- 累计预扣七档临界值、速算扣除数和月度递进。
- 年中接入期初累计值。
- 当月税额负数时归零。
- 分级金额精确到分。
- 扣款大于应发时拒绝确认。

### API 与权限测试

- 无会话、无 `salary.manage` 权限和跨组织员工 ID 均被拒绝。
- 客户端伪造应发、个税或实发金额不会影响服务端结果。
- 预览与保存使用同一计算器，结果一致。
- 并发保存不会产生两张有效工资单。

### 页面与端到端测试

- 设置政策、预览、保存草稿、确认、本人查看全流程。
- CEO/财务可管理，员工只能查看本人。
- 桌面端和 390px 移动端金额、折叠明细和触摸目标可用。
- 旧工资单仍按历史手工记录展示。

## 10. 发布边界

数据库迁移先增加新表和可空字段，不删除或改写现有工资数据。新计算功能在有效政策启用后开放；没有政策的组织继续只读查看历史工资单。部署后先用测试员工和测试月份完成一笔完整核算，再允许真实工资确认。
